2. WHAT BOREA IS INTENDED TO BE

A distro-agnostic online Linux installer and powerful, beautifully minimal landing
pad. The main application is a native Rust GUI. A smaller Rust TUI downloads,
verifies, and launches the project as a prebuilt installer bundle. Limine is the
preferred bootloader integration.

The landing pad automatically scans local hardware, offers integrated Wi-Fi,
helps the user choose a distribution and edition, resolves its latest release,
and guides configuration, explicit disk review, installation, and completion.
After installation, each distribution keeps its native maintenance/update model.

The visual identity centers on wind: quiet animated airflow, generous whitespace,
minimal controls, warm ivory/charcoal themes, and a restrained blue-green accent.

4. LATEST-RELEASE POLICY

  - Resolve latest when preparing an install, not through a permanently hardcoded
    version in the interface.
  - Arch uses current rolling repositories. Fedora and Debian default to latest
    stable/GA, not Fedora Rawhide/beta or Debian testing/unstable.
  - Derivatives follow their own official stable or rolling channels.
  - Tumbleweed uses a current coherent published snapshot.
  - Display exact resolved identity and metadata freshness.
  - Pin artifacts, hashes/digests, repository identities, adapter/catalog versions,
    image variant, and package policy into the reviewed installation plan.
  - Do not chase moving latest references while executing an approved plan.
  - If latest is unqualified, show integration pending. Never silently substitute
    an older certified release or claim cached metadata proves current latest.

No release resolver or signed production catalog has been implemented yet.

5. AUTOMATIC HARDWARE AND WI-FI REQUIREMENTS

Hardware discovery is local, progressive, asynchronous, and read-only. Scan CPU
architecture/instruction sets, every GPU, RAM, storage topology and active mounts,
network/Bluetooth adapters, firmware mode/Secure Boot, displays/input, and device
type. Keep unknown distinct from unsupported. Track hybrid GPUs and hotplug.

Recommend compatible images, drivers, firmware, and device presets with reasons.
Never automatically select or approve a disk to erase.

Integrated Wi-Fi belongs in both frontends. The TUI must connect before needing
the GUI download. The proposed shared client uses NetworkManager D-Bus via zbus.
Support network discovery, signal/security, WPA2/WPA3 personal, hidden networks,
password handling, reconnect, disconnect, radio/rfkill diagnostics, and accurate
connectivity/captive-portal errors. Enterprise flows require reviewed certificate
handling or an explicit supported system-editor path.

Keep credentials out of command arguments, logs, plans, and support exports.
Transferring a live-session connection into the target requires an explicit choice
and secure adapter support. A live host must already have usable network drivers,
firmware, NetworkManager, and the system bus; later Borea Live can provide these.

Hardware scanning and NetworkManager Wi-Fi are implemented (see sections 13-14).

6. TUMBLEWEED GAMING + FIRMWARE REQUIREMENTS

The reviewed, hardware-appropriate target package set is intended to include:
  - Steam and native Proton prerequisites.
  - Lutris and a supported Wine stack.
  - MangoHud, GameMode, and Gamescope where compatible.
  - Appropriate 64-bit and required 32-bit graphics/Vulkan libraries.
  - CPU microcode and device/network/Bluetooth firmware.
  - Controller rules and supported handheld integration.

Resolve exact packages for the selected snapshot and disclose sources in review.
Optional launchers such as Heroic require reviewed availability. Do not silently
add third-party repositories or install every GPU branch on every machine.
Steam-managed runtimes may download on first use.

Firmware preinstallation means OS-loaded firmware packages and CPU microcode.
It does not authorize automatic BIOS/device firmware flashing.

No Tumbleweed adapter or gaming package installation has been implemented yet.

8. INSTALLATION AND BOOT DESIGN ALREADY DOCUMENTED

  - Unprivileged GUI/downloader; separately authorized privileged worker.
  - Typed plans and operations, explicit destructive review, target revalidation.
  - Authenticated local IPC, protected verified worker handoff, install locking.
  - Repository/release verification, bounded downloads, safe archive extraction.
  - Secrets excluded from normal serialization, logs, and exported plans.
  - Stage progress, safe cancellation boundaries, redacted diagnostics/journals.
  - Native bootstrap/deployment, target account/network/services configuration.
  - Limine boot artifacts and kernel/initramfs update lifecycle.
  - Failure recovery semantics without promising rollback after disk erasure.

The first proposed vertical slice is x86-64 UEFI with Secure Boot disabled, an
Arch target (built from upstream tools, run from Borea Live and from a live session
of another family; see section 13), one explicitly erasable disk, GPT, FAT32 ESP and ext4 root. The ESP
baseline is 2 GiB subject to calculated artifact/upgrade/reserve requirements.

The initial simple layout does not constrain the complete requested catalog.
Adapters must preserve required encryption/layout/security and native update
semantics, including Fedora SELinux, Omarchy's selected upstream requirements,
Tumbleweed conventions, and Bazzite's image deployment/update/rollback behavior.

Limine remains preferred. Exact version, configuration syntax, paths, and kernel
protocol must be proven. First boot alone is insufficient: test a native kernel
upgrade and reboot. Bazzite needs separate deployment-aware boot integration;
no generic DNF install-root approximation or silent bootloader replacement.

No actual disk operations, distro integration, Limine setup, boot checks, or
kernel-update hooks have been implemented or validated in this session.

17. BOREA-FLASH: WRITE BOREA LIVE TO A USB STICK (22 October 2026)

crates/borea-flash builds `borea-flash`, a ratatui TUI (ratatui 0.30):
  - image.rs: accepts only hybrid ISO 9660 images (PVD "CD001", MBR 0x55AA),
    reads the volume label, finds a published SHA-256 (<iso>.sha256, SHA256SUMS)
    and checks it on a worker thread; a mismatch blocks writing.
  - target.rs: candidates are removable/USB disks only. Verdicts: Ready, Mounted
    (press u to unmount via UDisks2), or Refused (runs this system, holds the
    image, followed through LUKS/LVM sysfs slaves; too small; swap; installer
    medium in a live session).
  - write.rs: 4 MiB chunks, fsync, posix_fadvise DONTNEED (rustix, no unsafe),
    then byte-for-byte read-back verification; cancellation between chunks.
  - device.rs: root opens /dev/<name> with O_EXCL; otherwise UDisks2
    Block.OpenDevice("rw", O_EXCL) through polkit. Unmount and eject (PowerOff)
    also go through UDisks2.
  - app.rs: screens Choose, Confirm (type the device name), Working (gauge,
    speed, time left, stop asks first), Finished (verified/stopped/failed, eject).
    Keys in, Requests out; the main loop runs them on threads and re-checks the
    stick right before opening it.
  - 16 tests: image parsing and checksums, verdicts, sysfs disk-of-file through
    dm, the writer against image files (success, corrupted byte caught,
    cancel), and every TUI screen through ratatui TestBackend.
  - Checked on the maintainer's laptop with --list only: the internal NVMe is not
    offered; the USB holding a mounted Omarchy installer shows as needing unmount.
    No real device has been written by this session.
