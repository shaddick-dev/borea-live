# Disposable UEFI installation tests

These tests never attach a host block device. The Rust guest binary refuses to run without its explicit QEMU firmware marker and a target with serial `BOREA-TEST-TARGET`. The runner attaches `/work/target.qcow2` (40 GiB sparse, or 100 GiB for alongside) and copied OVMF variables. Secure Boot installs also attach a read-only virtual FAT directory containing the signed live boot chain. Its public test password is a fixture, never a product default.

Build `borea-vm-test` and `borea-vm-runner` from the backend workspace, and build `borea-firstboot` for `x86_64-unknown-linux-musl`. Stage that static helper alongside the native test binaries; a dynamically linked target helper is rejected. Build this directory's Dockerfile as `borea-vm-test:kernel`. Prepare a disposable bind-mounted work directory with marker file `.borea-test-workdir` containing `BOREA_TEST_WORK`, copies of `init` as `test-init` and `borea-dhcp`, and the public `dist/keys/*.gpg` under `keyrings/`.

Inside the tools container, mount that directory at `/work`, staged backend binaries read-only at `/binaries`, and the host's public combined CA bundle read-only at `/run/borea-ca.pem`. Ensure the staged `borea-firstboot` is the static binary. Run `build-initrd.sh`; then `/binaries/borea-vm-runner` to install and `/binaries/borea-vm-runner boot` to boot the installed disk. Preserve the same OVMF variables and scenario settings between these commands. Set `BOREA_TEST_DISTRO=arch|debian|fedora|opensuse`, `BOREA_TEST_LAYOUT=whole|alongside`, and `BOREA_TEST_SECURE_BOOT=0|1`. Use a separate work directory per scenario; the runner refuses a mismatch. This environment has no KVM device, so local runs use slow TCG emulation. The runner uses KVM when an accessible `/dev/kvm` has explicitly been provided to the tools container.

No privileged container flag or host device bind is needed. The live guest trusts the session CA only in RAM via fw_cfg. The proxy is passed through an anonymous memfd, not a command-line credential or saved file. Do not bake session trust into an image layer. Public upstream verification keys are separate from session transport trust.

Installation logs are redacted. The boot console checks disk unlock, the account, distribution, network and sudo before powering off. A kernel panic, timeout, missing completion marker or failed assertion is a failing test. A successful planner matrix alone is not an installed-system test.

The alongside guest constructs a 100 MiB FAT ESP, Microsoft-reserved partition and NTFS data partition on its explicitly named test disk. It checks the original NTFS UUID, resized geometry, data file, Microsoft loader sentinel and fallback loader sentinel after installation. These are synthetic preservation fixtures, not a real Windows installation or Windows boot certification.

Secure Boot scenarios use Microsoft-enrolled OVMF variables and a signed Debian shim → GRUB → kernel chain for the live environment, regardless of the selected target distro. The guest refuses to proceed if the firmware does not actually report Secure Boot enabled. Boot assertions check it again in the installed OS. The Microsoft-enrolled fixture deliberately refuses Arch: Arch's owner-key enrollment starts from Setup Mode and needs separate firmware enrollment automation. Missing installed-system evidence remains a release gate in `docs/VERIFIED.md`.

The qcow2 test drive uses QEMU `cache=unsafe` only to reduce fsync overhead under TCG. It is disposable and is not a power-loss durability test; production disk I/O is unchanged.

The `backend-vm.yml` workflow runs the four whole-drive, Secure Boot-off scenarios nightly. A manual run can select a distribution, both layouts and both firmware policies. The Microsoft-enrolled matrix excludes Arch Secure Boot; it does not certify owner-key enrollment. A shared build job produces fresh native test drivers and a static target helper once for the matrix. Each scenario stages those artifacts before constructing its initrd, installs and then boots, and uploads the console even on failure. An available KVM device is passed explicitly; no host disks are passed.

`borea-vm-runner preflight` runs only signed tool-root acquisition and native metadata preparation. The guest compares kernel disk-write counters before and after, and refuses any change. It requires the whole-drive fixture. `repair` is a separate diagnostic mode for the Debian whole-drive fixture; a repaired boot is never reported as an uninterrupted install pass. Debian-based live environments need the `fdisk` package for `sfdisk`, in addition to `util-linux`.

The additional ignored `borea-disk` native test runs only with `BOREA_TEST_NTFS_IMAGE` pointing to a regular NTFS image under `/fixtures`, alongside a `.borea-ntfs-fixture` marker containing `BOREA_TEST_NTFS`. Build its unit-test binary with `cargo test -p borea-disk --lib --no-run`, then run it with `--ignored --nocapture` inside the tools container after formatting a disposable 256 MiB regular file using `mkfs.ntfs --fast --force`. It hashes the entire image around each read-only probe and checks absent, inactive and active hibernation states. Never point this fixture test at a block device.
